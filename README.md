# Корсик · ПОЛИПЛАСТИК — RAG-ассистент для онбординга (MVP, чекпоинт 2)

```
 HR ──► admin :8003 ──► ingest :8002 ──► llm-gateway :8001 ──► OpenRouter (embeddings)
          │               │  PDF/PPTX/DOCX → текст (текстовый слой / Tesseract OCR)
          │               └──► Qdrant :6333
          └──► pipeline :8004 ◄── MAX (long polling / webhook)
                 агент (tools: search_knowledge_base, escalate_to_hr) ──► llm-gateway (chat)
                 sentiment + темы + красные флаги ──► аналитика / эскалации

 PostgreSQL :5432 — одна база `korsik`, у каждого сервиса своя схема: pipeline · ingest · admin · gateway
```

| Сервис | Порт | Назначение |
|---|---|---|
| admin | 8003 | Панель управления HR (Basic-auth `ADMIN_USER`/`ADMIN_PASSWORD`): загрузка документов, просмотр OCR-текста, аналитика, эскалации, переключатель канала |
| pipeline | 8004 | Агент, планировщик, бот MAX (long polling или webhook `/max/webhook`) |
| ingest | 8002 | OCR → чанки → эмбеддинги → Qdrant, `/search` |
| llm-gateway | 8001 | Роутинг chat/embeddings; провайдер меняется переменными `LLM_PROVIDER`/`EMBED_PROVIDER` (`openrouter` или `custom`) |
| postgres | 5432 (только 127.0.0.1) | Реляционная БД PostgreSQL 16: сотрудники, переписки, обращения, аналитика, пользователи панели, документы, расход модели. Схемы создаются сервисами при старте (идемпотентно) |
| qdrant | 6333 | Векторная БД |

## Запуск
```bash
cp .env.example .env        # вписать OPENROUTER_API_KEY, ADMIN_PASSWORD (и при желании POSTGRES_PASSWORD)
docker compose up -d --build
python scripts/seed.py ПОЛИПЛАСТИК/      # загрузить регламенты (или через панель управления)
```
Панель управления: http://localhost:8003

Сервисы стартуют после готовности PostgreSQL (healthcheck) и работают не от root; у каждого есть `HEALTHCHECK` (`docker compose ps`).

### Переход со старой версии (SQLite → PostgreSQL)
Данные из `pipeline.db`, `ingest.db` и `admin.db` переносятся одной командой, файлы документов и картинки остаются в прежних томах:
```bash
docker compose up -d --build                        # сервисы создадут схемы в PostgreSQL
mkdir -p migrate && for s in pipeline ingest admin; do docker compose cp $s:/data/$s.db ./migrate/; done
pip install "psycopg[binary]"
python scripts/migrate_sqlite_to_postgres.py --dsn postgresql://korsik:ПАРОЛЬ@127.0.0.1:5432/korsik --dir ./migrate
```
Скрипт идемпотентен (повторный запуск ничего не дублирует) и выравнивает счётчики id. Проверен на копиях рабочих баз.

## Канал: MAX
Бот работает только в MAX (токен — `MAX_BOT_TOKEN` в `.env`; long polling для разработки, webhook для продакшена — `MAX_TRANSPORT`). Подписки и команды `/` публикуются из вкладки «Команды».
**Webhook принимает события только с секретом:** без `MAX_WEBHOOK_SECRET` маршрут `/max/webhook` отвечает `503`, а подписка не создаётся (иначе любой мог бы прислать поддельное событие «от имени сотрудника»).
**Надёжность:** события записываются в таблицу `inbox` до обработки; отправка в МАКС повторяется (3 попытки), сотрудник при сбое получает извинение, а не тишину; прерванные остановкой сервиса события доводятся после запуска. Сбои видны в статусе канала (`inbox.failed`). События одного пользователя обрабатываются строго по очереди (рассылка планировщика и диалог не затирают состояние друг друга).

## Смена модели/провайдера
`.env`: `LLM_MODEL`, `EMBED_MODEL`, `LLM_PROVIDER=custom` + `CUSTOM_BASE_URL` — клиентам менять ничего не нужно.
Смена эмбеддинг-модели меняет размерность → задайте новый `QDRANT_COLLECTION` и перезагрузите документы.

## Тесты
Тесты идут в настоящем PostgreSQL (SQL-диалект важен). `./scripts/test_all.sh` сам поднимает временный контейнер `postgres:16-alpine` (нужен docker) либо использует `TEST_DATABASE_URL=postgresql://user:pass@host:port/db`. В CI (`.github/workflows/ci.yml`) база — сервис postgres; там же линтер (`ruff`), анализ безопасности (`bandit`) и порог покрытия.
Зависимости управляются через [uv](https://docs.astral.sh/uv/): у каждого сервиса свои `pyproject.toml` и `uv.lock` (группа `dev` — pytest, pytest-asyncio, pytest-cov, respx).
- Установка uv: `pip install uv` (в виртуальном окружении) или официальный установщик.
- Тесты всех сервисов с покрытием строк и ветвей: `./scripts/test_all.sh`; одного сервиса: `cd services/pipeline && TEST_DATABASE_URL=… uv run pytest`.
- Добавить зависимость: `cd services/<сервис> && uv add <пакет>` (обновит `pyproject.toml` и `uv.lock`); образы собираются по `uv.lock` (`uv sync --frozen`).

## Защита от галлюцинаций
Фактические ответы — только по найденным фрагментам (порог `RAG_MIN_SCORE` (по умолчанию 0.5)); нет релевантного — бот молчит, а вопрос сразу уходит HR; индивидуальные кадровые вопросы → `escalate_to_hr` (передаётся сразу).

## Онбординг по сценарию из ТЗ
Панель управления → «Сотрудники»: создайте сотрудника (площадка, дата выхода) → привяжите к MAX/веб-пользователю (ссылка `?start=КОД` или `/start КОД`) →
бот сам ведёт его по таймлайну (за день до выхода → первый день → опросы → конец испытательного срока). Сценарий — `services/pipeline/app/scenario.py`
(тексты из ТЗ, правятся в панели управления → «Сценарий»), движок — `engine.py`, персона нейросети — `style.py`.
Тесты автономным агентом: `CLAUDE_TEST_RUNBOOK.md` (генерируется `scripts/gen_runbook.py`); ручной быстрый прогон — `MAX_TEST.md`.

### Передача HR и команды
**Бесшовная эскалация:** обращение для HR создаётся сразу, без кнопок и подтверждений сотрудника. Если Корсик не знает ответа (в базе знаний ничего релевантного), он **ничего не пишет в чат** — вопрос сразу появляется в панели управления → «Эскалации» (тип «нет ответа в базе — передано автоматически»); HR отвечает из панели, и ответ приходит сотруднику в МАКС. Личные и тревожные вопросы (зарплата, конфликт, увольнение, просьба о человеке): бот отвечает и сразу передаёт HR. Технический сбой поиска или модели — не «не знаю»: бот пишет о неполадках, обращение не создаётся. «Связаться с рекрутером», `/HR` и «Передать HR через Корсика» (сотрудник описывает проблему одним сообщением) тоже передают сразу.
Команды бота (подсказки при вводе «/») — в панели управления → «Команды»: свои команды с фиксированным ответом или ответом из базы знаний; подсказки в MAX обновляются автоматически.

## Картинки Корсика и интент «обратиться к HR»
- Картинки в образ не входят: их загружают через панель управления (вкладка «Сценарий» → «Библиотека картинок» или кнопка у сообщения) либо через API
  (`POST /api/scenario/images?name=…` — тело: JPEG/PNG; `PUT /api/scenario/image` — назначить сообщению; `DELETE /api/scenario/images/{файл}`).
  Веб отдаёт их по `/assets/<файл>`, в MAX они загружаются через `/uploads` и кэшируются; если загрузка не удалась — уходит текст без картинки.
- Если вопрос по смыслу похож на эскалацию (конфликт, зарплата/выплаты, увольнение, жалоба, здоровье/безопасность, просьба о живом человеке),
  бот отвечает как обычно, а обращение для HR создаётся сразу.
  Правила — `services/pipeline/app/intent.py`.

## Роли в панели управления (RBAC)
Вход — Basic-auth. Администратор из `.env` (`ADMIN_USER`/`ADMIN_PASSWORD`) есть всегда; остальных создаёт администратор во вкладке «Пользователи» (хранятся в PostgreSQL, схема `admin`, пароли — scrypt).
Читать могут все роли, менять — только по праву на раздел (проверка на сервере в прокси панели управления, кнопки в интерфейсе блокируются):

| Роль | Может менять |
|---|---|
| Администратор | всё, включая канал доставки и пользователей |
| Контент-менеджер | база знаний, сценарий (тексты, картинки), команды бота |
| HR-специалист | сотрудники и онбординг, обращения (ответы сотрудникам) |
| Наблюдатель | ничего (только просмотр) |

Журнал изменений (кто и что менял) — во вкладке «Пользователи». Правила — `services/admin/app/rbac.py`.

## Аналитика, руководители и дайджест
- Вкладка «Аналитика» интерактивна: фильтры (период, площадка, руководитель) меняют все блоки; клик по столбцу дня, теме, этапу, красному флагу или строке опроса открывает список сообщений, клик по сотруднику — диалог. В общую статистику (вопросы, пользователи, графики по дням, детализация) входят только сообщения сотрудников с оценкой тональности: нажатия кнопок, «/»-команды и короткие ответы опросов («9», «да») оценки не получают и не считаются. Есть тултипы, воронка сценария, зона риска (индекс 0–100) и **светофор «Статус адаптации»** (см. ниже).
- **Светофор «Статус адаптации»** (вкладка «Аналитика», верхний блок): строка на каждого новичка — цвет, фаза, прогресс по этапам сценария, последний пройденный и ближайший этап, причины цвета. Нажатие на цвет фильтрует список, на строку — открывает диалог. Правила (`services/pipeline/app/insights.py`, `status()`; API `GET /api/insights/status`):
  🔴 красный — высокий риск ухода (индекс ≥ 50) или сбой доставки этапа; 🟡 жёлтый — средний риск (25–49), пропущенные этапы, наступивший, но не отправленный этап, вопрос без ответа больше суток, либо новичок не привязан к боту, а выход уже сегодня/завтра; 🟢 зелёный — тревожных сигналов нет; ⚪ серый — ещё не подключён к боту. Сортировка: красные → жёлтые → зелёные → серые. Фильтры периода/площадки/руководителя действуют на блок; руководитель подразделения видит только своих подчинённых.
- Руководитель подразделения: в карточке сотрудника указывается руководитель (ФИО и, для push, ID его чата в MAX). Пользователь панели управления с ролью «Руководитель подразделения» видит только своих подчинённых; бот напоминает о личных встречах (3-й день, 2 недели, месяц, 2 месяца, за неделю до конца испытательного срока, при высоком риске).
- Еженедельный дайджест «Настроения в коллективе новичков» (понедельник 9:00) уходит получателям, заданным во вкладке «Аналитика»; можно сформировать и отправить вручную.
- Вложения: в библиотеку сценария загружаются картинки (JPEG/PNG) и PDF; их назначают сообщениям в панели управления или через API.
- Сверка с кейсом — `CASE_COVERAGE.md`.

## Редактор сценария и площадки
- «Сценарий» в панели: этапы можно добавлять, удалять (кроме знакомства), переставлять ↑↓, менять название, время отправки (от даты выхода или конца испытательного срока: месяцы + дни, рабочие/календарные, время), площадки и офис/не офис, «ждать отмашки рекрутера», «это опрос». Внутри этапа — добавление, удаление и перестановка сообщений и вопросов (сообщение, открытый вопрос, шкала, да/нет), правка текстов, вложений и площадок.
- Разделение по площадкам: у каждого этапа и сообщения отмечаются площадки (пусто — для всех); фильтр «Показать площадку» показывает сценарий глазами выбранной площадки; «Копия для площадки…» делает копию этапа.
- Площадки добавляются, переименовываются и удаляются в блоке «Площадки»; новая может получить содержание «как у» существующей. Удаление убирает и то, что было только для неё; площадку с сотрудниками удалить нельзя.
- «Вернуть исходный сценарий» восстанавливает сценарий из ТЗ. Сценарий и площадки хранятся в PostgreSQL (схема `pipeline`); файлы картинок и PDF — в томе `pipeline_data`.
- В таблицах есть фильтры: документы (статус, поиск), сотрудники (площадка, руководитель, привязка, поиск), обращения (статус, площадка, тональность, поиск), аналитика (период, площадка, руководитель).
- Пароли пользователей панели хранятся в виде хеша scrypt с индивидуальной солью (в базе нет открытого пароля); пароль главного администратора берётся из переменных окружения и в базу не пишется.

## Проверка вводимых данных
- **Сервер** (источник истины): все запросы проверяются; ошибка возвращается как `400` с понятным текстом на русском («Имя: слишком короткое значение (минимум 2 симв.)», «конец испытательного срока должен быть после даты выхода…»).
  Проверяются: ФИО (буквы, 2–100 символов, без спецсимволов), даты (формат ГГГГ-ММ-ДД, разумные пределы, конец испытательного срока позже выхода и не позже, чем через год), площадка (должна существовать), ID чатов и получателей дайджеста, адрес вебхука (только https), длины текстов (сообщение боту до 4000, ответ HR до 4000, текст сообщения сценария до 3500, название этапа до 120), количество элементов, формат и размер вложений (JPEG/PNG/PDF до 8 МБ, документы — расширение + содержимое, до 100 МБ), фильтры аналитики, а для пользователей панели — логин, имя и пароль (8–128 символов, буква и цифра, не равен логину).
  Слишком длинные тексты отклоняются, а не обрезаются молча.
- **Интерфейс**: поля формы ограничены атрибутами (`required`, `maxlength`, `pattern`, `min`/`max`) и проверяются перед отправкой; неверное поле подсвечивается подсказкой, файлы проверяются по типу и размеру ещё до загрузки.
- Правила — `services/pipeline/app/validation.py`, `services/admin/app/validation.py`, модели запросов в `main.py`.

## Базовые документы и сброс данных
- **Базовые документы** — регламенты в папке `BASE_DOCS_DIR` (в `.env`, по умолчанию `./base_docs`). При запуске `ingest` сам загружает их в базу знаний (OCR + векторы), изменённые файлы перезагружает, убранные из папки — удаляет. В панели они помечены «базовый» и не удаляются кнопкой. Документы, загруженные вручную, живут отдельно. Подробнее — `base_docs/README.md`.
- **Сброс до исходного состояния:** `./scripts/reset_data.sh` (с подтверждением, `--yes` — без). Удаляет сотрудников, переписки, обращения, аналитику, ответы опросов, напоминания, пользователей панели и журнал действий, документы, загруженные вручную. Остаются: сценарий (исходный, с выбранными вложениями), библиотека картинок и файлов, площадки и команды по умолчанию, базовые документы, главный администратор. Перед сбросом дамп базы сохраняется в `backups/<дата>/korsik.sql` (папка не в git; восстановить: `docker compose exec -T postgres psql -U korsik korsik < backups/<дата>/korsik.sql`).

## Качество поиска (RAG): как измерить
`python scripts/eval_rag.py --ingest http://127.0.0.1:8002` прогоняет контрольные вопросы `eval/rag_questions.jsonl` (21 вопрос с ответом в регламентах и 8 без ответа) через поиск и показывает: нашёлся ли нужный фрагмент (hit@1, hit@k, MRR), ответит ли бот при текущем пороге `RAG_MIN_SCORE` и промолчит ли там, где ответа нет; перебирает пороги и подсказывает лучший. Ключ LLM не нужен — только эмбеддинги. `--validate base_docs` проверяет сам набор по локальным файлам (для сканов без текстового слоя — через стек).

## Расход модели и стоимость
Шлюз считает токены каждого запроса по дням и моделям (таблица `gateway.llm_usage`), `GET /usage?days=30` (порт 8001, только с хоста) отдаёт сводку. Если в `.env` заданы цены за 1 млн токенов (`LLM_PRICE_IN`, `LLM_PRICE_OUT`, `EMBED_PRICE`, `PRICE_CURRENCY`), добавляется стоимость. В панели управления → «Аналитика» это плитка «Расход модели»; рядом — «Закрыто без HR» (доля вопросов, которые бот закрыл сам).

## Безопасность интерфейса и данных (кратко)
- Интерфейс панели не встраивает данные из базы в JS-обработчики: названия документов, ФИО и тексты берутся по id (раньше апостроф в названии документа или ФИО руководителя позволял выполнить чужой скрипт). Каждый ответ панели несёт CSP, `X-Frame-Options: DENY`, `X-Content-Type-Options`, `Referrer-Policy`.
- Тексты из базы знаний подаются модели как справочные данные: инструкции внутри документов не выполняются.
- Повторные автоматические обращения (нет ответа в базе, красный флаг, решение модели) за сутки склеиваются в одно обращение со счётчиком, а не множатся.
- Расчёты дашборда (риск, светофор, воронка) пакетные и кэшируются на `INSIGHTS_CACHE_TTL` секунд (15 по умолчанию, 0 — выключить): на 1000 новичков светофор считается за ~0,2 с.
